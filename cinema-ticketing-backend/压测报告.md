# 影院项目并发一致性实测报告

> **2026-09-26 复测说明：** 当前代码的 `OrderConcurrencyConsistencyTest` 已通过，四个场景各重复三轮。重复锁定、重复下单、超卖和重复支付均为 0；下单的并发冲突异常和支付补偿查询异常也均为 0。当前实现已使用用户行锁串行处理同一用户的下单请求，以及订单行锁处理支付，本文第四节记录的是 9 月 21 日的历史问题，本次复测没有复现。测试仍直接调用 Service，并模拟消息发布器，不代表 HTTP 吞吐量或 RabbitMQ 整条链路已经完成压力测试。

> 实测时间：2026-09-21
> 环境：Windows 11 / Java 21 / Spring Boot 3.4.5 / **真实 Redis**（embedded-redis 5.0.14）+ **真实 MySQL 8.0.44**
> 复现命令：`mvn -Dtest=OrderConcurrencyConsistencyTest test`

## 一、为什么要实测

项目里原有的 7 个测试文件全是 Mockito 单测，其中锁座相关的断言是这样写的：

```java
// OrderServiceCoreFlowTest.java:43
when(redisTemplate.execute(any(DefaultRedisScript.class), any(List.class), eq("owner"), anyString()))
        .thenReturn(0L);
```

**Lua 脚本从未被执行过，唯一索引从未被查询过** —— 测试直接伪造了返回值来验证 Java 的 if 分支。这种测试可以证明控制流写对了，但**产不出任何"0 笔"的数字**，因为数据库里根本没有数据。

所以本报告的所有数字，都来自真跑：真 Redis 执行真 Lua，真 MySQL 执行真约束，真线程池制造真并发。

## 三、可以直接写进简历的句子

> 针对高并发选座场景下的超卖与重复下单问题，采用 **Redis Lua 脚本原子锁座 + 请求号唯一索引幂等** 方案；在 200 并发抢同一座位、300 并发抢 50 个座位的实测中，**重复锁定 0 次、超卖 0 笔、重复下单 0 笔、重复支付 0 笔**。

**不要写 QPS。** 这套测试测的是"并发下数据有没有写坏"，不是吞吐量。它没有经过 HTTP 层、没有 Nginx、连接池上限 64，拿它宣称 QPS 会在面试时被追问穿。

## 四、实测中发现的两个真实缺陷

这两个缺陷**不影响上面四个数字**（数据是对的），但会让并发调用方拿到 500。诚实地说，这是本次实测比"确认幂等生效"更有价值的产出。

### 缺陷 1：并发重复下单，输的请求返回 500

`OrderService.createOrder` 的幂等是"先查后插"：

```java
// OrderService.java:68
String existingOrderNo = findOrderNoByRequest(userId, request.requestId);
if (existingOrderNo != null) { return findOrder(userId, existingOrderNo); }
...
// OrderService.java:82 —— 没有 try/catch
jdbcTemplate.update("INSERT INTO order_idempotency (user_id, request_id, order_no) VALUES (?, ?, ?)", ...);
```

并发时多个线程同时查到 null，抢着插入，**只有一个能成功**，其余抛 `DuplicateKeyException`。而 `GlobalExceptionHandler` 只显式处理了 `BusinessException`、参数校验和 `ConstraintViolation`，`DuplicateKeyException` 落到兜底的 `@ExceptionHandler(Exception.class)` → **HTTP 500**。

实测：100 并发中最多 **63 个请求返回 500**（每轮 63 / 46 / 22，取决于线程碰撞的时机）。

**数据没错**（唯一索引兜住了，只有 1 笔订单入库），但调用方看到的是报错，而不是"你刚才那单已经下好了"。前端如果据此提示"下单失败"，用户会重复付款。

**修法**：把插入包在 try/catch 里，捕获 `DuplicateKeyException` 后重查 `order_idempotency` 返回已有订单 —— 与 `pay()` 已有的写法一致。

### 缺陷 2：支付幂等的补偿查询本身失效（更严重）

`OrderService.pay` 的幂等**有**补偿逻辑，但那个补偿读不到数据：

```java
// OrderService.java:99-108
try {
    jdbcTemplate.update("INSERT INTO payment_transaction (payment_no, order_id, ...) VALUES (?, ?, ...)", ...);
} catch (DuplicateKeyException exception) {
    Map<String, Object> existing = jdbcTemplate.queryForMap(
            "SELECT order_id FROM payment_transaction WHERE payment_no = ?", paymentNo);   // ← 查不到
    ...
}
```

`pay()` 整体是 `@Transactional`。MySQL 默认隔离级别是 **REPEATABLE READ**，输的线程在事务开始时就固定了快照；赢的线程是在它拿到 `DuplicateKeyException` **之后才提交**的。于是这条补偿 `SELECT` 在自己的快照里看不到那一行，`queryForMap` 期望 1 行、实得 0 行，抛 **`EmptyResultDataAccessException: Incorrect result size: expected 1, actual 0`** —— 同样落到兜底分支变成 500。

实测：50 并发中 **最多 49 个请求返回 500**，只有 1~8 个真正成功返回。

**修法**（任选其一）：
- 补偿查询用当前读绕开快照：`SELECT ... FOR UPDATE` 或 `LOCK IN SHARE MODE`；
- 或把补偿查询放到事务外（`REQUIRES_NEW`）；
- 或干脆先 `INSERT IGNORE`，再读。

### 两个缺陷的共同根源

`GlobalExceptionHandler` 缺 `DuplicateKeyException` / `DataAccessException` 的分支，所有并发冲突都退化成 500。见 [GlobalExceptionHandler.java:37](src/main/java/com/cinema/ticketing/common/GlobalExceptionHandler.java#L37)。建议补一个 `@ExceptionHandler(DuplicateKeyException.class)` 映射到 409。

> 另有一个独立的限流绕过问题（`RateLimitFilter` 信任客户端自报的 `X-Trusted-Proxy` 头），不在本次测试范围内，另行处理。

## 五、测试怎么设计的

关键决策是**不用 `@MockBean` 起完整 Spring 上下文，而是手工搭最小上下文**：

```java
@Configuration
@EnableTransactionManagement
static class TestConfig {
    @Bean DataSource dataSource()                    { /* HikariCP → 真实 MySQL */ }
    @Bean PlatformTransactionManager transactionManager(DataSource ds)
                                                     { return new DataSourceTransactionManager(ds); }
    @Bean RedisConnectionFactory redisConnectionFactory()
                                                     { /* Lettuce → 内嵌真实 Redis */ }
    @Bean OrderMessagePublisher orderMessagePublisher() { return mock(OrderMessagePublisher.class); }
    @Bean OrderService orderService(...)             { return new OrderService(...); }
}
```

原因有三：

1. **必须有真的 `@Transactional` 代理。** 如果不用 Spring 而直接 `new OrderService(...)` 调用，唯一索引冲突时事务不会回滚，脏订单会留在库里 —— 测出来的"重复订单"数字就是假的。这是本测试唯一不能省的东西。
2. **不需要 RabbitMQ。** `OrderMessagePublisher` 只是个薄封装，mock 掉即可；用 `@SpringBootTest` 反而要处理 `RabbitTemplate` 连接失败。
3. **不经过 HTTP。** 直接调 `OrderService`，可以任意构造 `owner`（锁持有者就是 auth token 字符串，见 [OrderController.java:42](src/main/java/com/cinema/ticketing/order/OrderController.java#L42)），既不需要真实登录，也绕开了限流器。

并发用 `CountDownLatch` 做起跑线，**等所有线程都停在 `await()` 之后才 `countDown()`**，保证是瞬时齐发而不是顺序调用。所有 `future.get()` 都带超时，避免死锁时挂住构建。

## 六、怎么复现

```bash
# 1. 建库建号（只需一次，用 root 执行）
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS cinema_ticketing DEFAULT CHARACTER SET utf8mb4; \
  CREATE USER IF NOT EXISTS 'cinema'@'localhost' IDENTIFIED BY 'cinema'; \
  GRANT ALL PRIVILEGES ON cinema_ticketing.* TO 'cinema'@'localhost'; FLUSH PRIVILEGES;"

# 2. 跑测试（内嵌 Redis 自动拉起，不需要本机装 Redis）
mvn -Dtest=OrderConcurrencyConsistencyTest test

# 3. 想保留测试数据做人工核查，加这个参数（默认跑完自动清理）
mvn -Dtest=OrderConcurrencyConsistencyTest -Dzzt.keepFixtures=true test
mysql -ucinema -pcinema cinema_ticketing < verify-consistency.sql
```

凭据从环境变量读，默认值与 `application.yml` 一致：`DB_USERNAME` / `DB_PASSWORD` / `DB_URL`。**源码里没有任何密码。**

## 七、这份测试的边界（面试时主动说，别等被问）

- **不含 HTTP 层**：Nginx、限流、序列化开销都没测。
- **连接池上限 64**：并发 200/300 的请求在池上会排队，所以这不是极限吞吐测试，而是正确性测试。
- **单机单实例**：没有验证多实例部署下 Redis 锁与 MySQL 的行为差异（不过锁在 Redis 里，本来就是跨实例共享的）。
- **RabbitMQ 被 mock**：超时取消链路的并发正确性（`cancelIfUnpaid` 的消息去重）**没有实测**，只有单测覆盖。想补的话是下一个测试的活。
- **内嵌 Redis 是 5.0.14**，生产用的镜像版本可能不同；`SET ... PX` 和 Lua 语义在这个范围内是稳定的。
