# Agent 完整学习路线：后端工程师转岗版

整理日期：2026-10-02。适用对象：已有后端开发经验，正在学习影院项目，准备转 Agent 相关岗位。默认求职方向为国内社会招聘；城市、工作年限和目标公司尚未限定。

这份路线包含：招聘要求、能力优先级、140 小时核心学习计划、影院项目改造路线、未来能力分支、前两周任务、作品集和面试准备。时间是学习规划估算，不是拿到 offer 的承诺。后文的改造、实验和评测均为建议任务，未表示当前项目已经实现或通过验证。

## 1. 先确定求职定位

**建议主攻：Agent 应用开发 / 大模型应用工程师 / AI 后端工程师。**

你已有的接口设计、数据库、鉴权、事务、缓存、消息队列、部署和故障排查经验，可以直接用于 Agent 系统。主要需要补齐：Python 异步开发、模型调用、工具编排、检索与上下文管理、效果评测。

按以下顺序选择方向：

1. **应用研发**：让 Agent 完成一个可验收的业务任务，例如查询订单、解释退款规则、生成带来源的答复。最适合作为当前主线。
2. **Agent 平台 / Infra**：多租户、任务执行、沙箱、资源调度、模型网关、可观测性。如果你已有较强分布式系统或云平台经验，可以提前加入这类岗位。
3. **FDE / 企业交付工程师**：深入客户业务，接入企业系统，完成部署、评测和上线。适合愿意沟通需求、接受现场交付的人；应确认出差要求。
4. **Agent 算法 / 模型训练**：SFT、偏好优化、强化学习、数据构建和模型实验。需要另补训练与数学能力，作为独立分支安排时间。

保留 Java 的业务工程优势，同时把 Python 补到能独立开发和排查服务的程度。先沿用项目的 Java + Python 架构，有针对性地理解跨服务的身份、超时和数据契约。

## 3. 学习优先级：先掌握什么

### 必须能独立完成

- Python 类型标注、Pydantic、异常、异步 HTTP、FastAPI、SSE，以及超时、取消和并发限制。
- LLM API 的消息结构、上下文窗口、Token、流式输出、结构化输出、工具调用、限流和费用记录。
- 工具契约：名称、用途、输入输出、校验、身份来源、权限、错误语义、幂等。
- 单 Agent 执行循环、固定工作流、状态、退出条件、澄清、失败恢复。
- RAG 的数据清洗、切分、检索、重排、引用、权限与更新。
- 评测集、失败分类、任务成功率、质量回归、延迟与成本。
- 面向业务的鉴权、隔离、日志、监控、部署和故障处理。

### 核心掌握后补齐

- MCP 的工具接入、鉴权、传输方式和版本兼容。
- 会话状态、长期记忆和知识库各自的边界；上下文压缩与失效策略。
- 持久化任务、人工确认、恢复执行和重复副作用控制。
- 模型选择、路由、缓存、批处理、回退策略。
- 基本前端交互：流式文本、工具执行状态、取消和确认操作。

### 按目标岗位选择

- 平台方向：Kubernetes、沙箱隔离、配额、队列、任务调度、模型网关。
- 算法方向：PyTorch、训练数据、LoRA/SFT、偏好优化、强化学习和严谨的实验方法。
- 多模态方向：文档图像、表格、语音、视觉工具、流式语音交互。
- 跨系统协作方向：多 Agent、A2A、委派任务与产物验收。
- 私有化推理方向：推理服务、批处理、KV cache、量化与 GPU 资源管理。

这些选修分支不计入下面的 140 小时核心计划。选择一个方向深入即可，新增分支需要另行安排时间。

## 4. 先弄清这些概念，后面的代码才容易读

- **LLM**：根据输入生成输出的模型。输出存在不确定性，需要外部事实、校验和评测。
- **Workflow**：开发者预先定义主要执行路径，例如识别意图后调用指定工具。
- **Agent loop**：模型根据任务和工具结果决定下一步，程序负责执行、约束并判断何时停止。
- **Tool Calling**：模型提出调用哪个工具及其参数，应用校验并执行，再把结果送回模型。
- **RAG**：检索当前任务需要的资料，把证据放入模型输入。动态订单状态应从业务接口实时查询。
- **Context**：模型本次调用能看到的全部信息，包括指令、历史、工具说明和检索结果。
- **Memory**：跨交互保存并选择性取回的信息，需要定义归属、有效期、更新和删除。
- **Fine-tuning**：用数据调整模型行为。是否值得做，需要通过具体问题和评测判断。
- **MCP**：接入工具、资源和提示模板的标准接口。模型如何规划、业务如何授权仍需应用设计。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)
- **A2A**：面向 Agent 之间的互操作。先了解任务委派与结果交换，之后按跨系统需求实践。[A2A 官方文档](https://a2a-protocol.org/latest/)

固定工作流与自主执行循环都可以有业务价值，选择依据是任务需求、效果、延迟和成本。关于二者的概念区别，可以读 Anthropic 的基础文章；文章发布于 2024 年，具体 SDK 用法应以当前文档为准。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

## 5. 时间安排：140 小时核心路线

七阶段依次为 **10 + 20 + 20 + 25 + 25 + 20 + 20 = 140 小时**。对已有后端经验的人，这是一个可调整的起点；实际可能需要约 120—180 小时，取决于 Python 基础、调试耗时和项目深度。

- 每天 30 分钟、每周 7 天：每周 3.5 小时，140 小时约 **40 周**。
- 工作日每天 30 分钟、周末各 2 小时：每周 6.5 小时，约 **22 周**。
- 每周 10 小时：约 **14 周**。

建议先用第二种节奏规划；如果周末无法增加时间，就采用第一种。以阶段完成标准推进，有基础的部分可以压缩，不能独立完成的部分增加练习。

每天半小时的默认分配：5 分钟回忆昨天，10 分钟读一小段代码或文档，10 分钟动手，5 分钟记录输入、输出和一个未解决问题。需要连续调试的任务放到周末。

### 阶段一：Python 与模型基础，10 小时

**目标：能读懂当前 Agent 服务的入口、数据结构和异步调用。**

学习内容：

- Python 的字典、列表、类型标注、装饰器、生成器、异常和上下文管理器。
- Pydantic 的输入输出模型、字段约束和错误处理。
- `async def`、`await`、`async for`、异步 HTTP、超时和取消。
- FastAPI 路由、依赖注入、配置、请求与响应。
- Token、上下文窗口、Embedding、概率生成、幻觉；理解训练与推理的区别。
- 数学先补向量相似度、概率、精确率/召回率的直觉，Transformer 学到能解释其基本作用。

影院练习：跟踪一个“查询本人订单”的请求；单独写一个小型异步查询函数，用固定返回值模拟 Java 接口，再替换为真实只读接口。

交付物：一页调用链笔记、一个可运行的小接口、5 个正常或异常输入案例。

完成标准：能解释每个 `await` 在等什么、异常在哪里转换、请求身份来自哪里；能说明 SSE 连接与后台持久任务的区别。

资源：[Python asyncio](https://docs.python.org/3/library/asyncio.html)、[FastAPI 并发与异步](https://fastapi.tiangolo.com/async/)。阅读时使用与项目安装版本相符的示例。

### 阶段二：原生模型调用与工具调用，20 小时

**目标：不依赖高层编排框架，也能实现一次完整的工具调用闭环。**

学习内容：

- 消息角色、结构化输出、JSON Schema、流式增量、用量记录。
- 完整闭环：发出模型请求 → 收到工具名和参数 → 校验并执行 → 回传工具结果 → 生成答复或继续调用。
- 参数格式正确与业务事实正确是两个独立问题。
- 工具名称与描述、参数边界、可重试错误、超时、限流和失败返回。
- 身份由服务端可信上下文提供，订单归属由业务层判断。

影院练习：选择一个可用模型，直接使用它的官方 API/SDK，实现 `search_screenings` 和 `query_order` 两个只读工具。用模拟数据覆盖正常、缺订单号、订单不存在、无权限和超时。起步阶段先限制为最多 3 次工具调用，再根据评测调整。

交付物：一个可运行的工具调用小程序、20 条案例、包含工具名/脱敏参数/耗时/结果状态的日志。

完成标准：能从日志还原执行过程；缺少必要参数时会澄清；模型提出无权限的调用时，应用能够阻止；能解释规则路由与模型选工具的区别。

选型方式：先读当前项目的 `model_config.py`，选一个你能稳定访问的供应商完成闭环。比较其他模型时复用同一评测集。供应商功能与价格变化较快，实际开发前查当前官方文档。

### 阶段三：编排、状态与上下文，20 小时

**目标：能根据任务设计执行路径，并约束模型自主程度。**

学习内容：

- 路由、分支、循环、状态更新和终止条件。
- 串行依赖与可以并行的独立查询。
- 超时预算、最大步骤数、重复调用检测、取消和人工确认。
- 会话状态、摘要、历史选择、工具结果裁剪；事实来源及有效期。
- 选 LangGraph 作为当前项目的主要编排练习工具，理解每层封装对应的实际调用。

影院练习：完成“查今晚某影院的电影，筛选两场并说明推荐原因”。分别做固定流程和受约束的工具循环，对比成功率、工具次数、耗时与费用。用 5 个多轮案例观察“它”“刚才那一场”等指代是否正确。

交付物：状态字段说明、两种实现的对比记录、步骤上限和失败处理策略。

完成标准：能说明为什么选择固定流程或动态循环；能找出上下文里哪些是用户描述、哪些是本轮可信业务结果；失败不会无限重试。

参考：上下文应按任务选择和维护，包括工具、历史和外部信息，而不是只修改提示词。[Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### 阶段四：完整 RAG 链路，25 小时

**目标：让知识问答有来源，能定位错误发生在检索还是生成阶段。**

学习内容：

- 文档清洗、标题层级、切分、重叠、元数据和版本。
- Embedding、关键词检索、向量检索、混合检索、Rerank。
- 检索前的租户/权限过滤、知识更新与删除、过期文档处理。
- 引用和证据对齐、证据不足时的澄清或拒答。
- 查询改写可能改变用户原意，必须记录并评测。

影院练习：准备 30—50 份自写或有权使用的规则资料，覆盖退票、会员、儿童票、异常购票。先测现有关键词检索，再增加一个向量存储，最后比较混合检索和重排。一次只改变一个主要因素。

存储选型先选一个即可。已有 PostgreSQL 运维经验可以考虑 pgvector；需要独立向量服务时可考察 Qdrant/Milvus。以过滤、更新、运维和数据规模作决定，不同时学习全部数据库。

交付物：文档处理脚本、索引版本记录、带来源的答复、检索对比报告。标注哪些案例必须调用实时订单接口。

完成标准：能展示“查不到”“查错了”“证据正确但回答错误”的案例；能解释切分和重排对你的数据是否有帮助；删除或失效的资料不会继续作为有效依据。

参考：[LangChain 检索文档](https://docs.langchain.com/oss/python/langchain/retrieval)。按官方当前页面及项目版本选择 API。

### 阶段五：评测、可观测性与安全，25 小时

**目标：回答“这个版本是否更好”时，有可重复的证据。**

评测从阶段一就开始积累，这一阶段把方法和工具完善。

学习内容：

- 任务输入、环境数据、预期结果、运行轨迹与评分方法。
- 区分开发调优集与保留评测集，记录模型、提示词、工具和数据版本。
- 使用程序规则检查确定性结果；对答案质量可加入模型评分，并用人工抽检校准。
- 记录 Trace ID、模型耗时、工具耗时、Token、错误、重试和终止原因。
- 学习提示注入、越权、跨租户泄漏、历史污染、工具输出不可信等问题。

影院练习：将评测集扩到至少 100 条，覆盖单轮、多轮、缺参数、非法参数、未登录、他人订单、知识过期、接口超时和注入文本。动态订单案例使用固定环境快照或可重置的测试数据，避免“标准答案”随数据库变化。

建议记录的指标：

1. **任务成功率**：完成业务验收条件的案例数 / 总案例数。
2. **工具调用质量**：工具选对比例、参数合法比例、未授权调用是否被阻止。
3. **检索效果**：有标注相关资料时计算 Recall@k，并抽查引用是否支持结论。
4. **体验**：首字延迟、完整答复耗时的 p50/p95、超时率。
5. **成本**：一次任务的总调用费用，以及总费用 / 成功任务数；计入失败和重试消耗。
6. **风险案例**：泄漏或越权案例数、错误写入数，逐条分析，不能被平均成功率掩盖。

工具先选一个可观测性平台即可，也可以从结构化日志开始。优先做到问题可追踪，再增加界面。

交付物：可重复运行的评测集、一次真实的前后对比、5 个失败案例复盘。

完成标准：能定位一次失败属于意图、参数、工具、权限、检索还是生成；改模型或提示词后有回归记录。通过有限评测集仅能说明该样本上的表现。

资源：[Anthropic Agent 评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

### 阶段六：MCP 与生产可靠性，20 小时

**目标：使工具可复用，长任务可恢复，系统行为可控制。**

学习内容：

- MCP 的 Host/Client/Server、Tools/Resources/Prompts、stdio 和 Streamable HTTP。
- 工具授权、身份传递、超时、并发、错误语义以及协议和 SDK 版本兼容。
- 任务状态持久化、检查点、恢复策略、人工确认和审计。
- 幂等键、事务边界、重试、队列投递与消费者重复执行。
- 模型服务限流、业务工具故障、客户端断开、预算耗尽的处理。

影院练习分成两项：

1. 将两个只读业务能力封装为 MCP Server，完成客户端接入并验证用户隔离。
2. 在独立练习环境模拟“生成退款申请草稿 → 人工确认 → 提交模拟业务操作”。中断后恢复，检查是否重复提交。使用假的订单和支付数据。

后端经验在这里会再次用到：Redis 可以承载缓存、限流或租约，但锁本身不能保证业务只执行一次；RabbitMQ 可以调度耗时任务，但消费者仍需设计幂等。`async/await` 解决进程内等待问题，也不会自动提供跨进程重启恢复。

交付物：MCP 接入说明、任务状态图、恢复演示、重复消息/超时/断线处理记录。

完成标准：能解释权限在哪里校验，任务进程中断后从哪里继续，哪些副作用可能重复，以及通过什么业务机制避免重复。

LangGraph 的持久化需要显式配置检查点及存储等机制；在依赖中加入 LangGraph 并不能证明系统具备恢复能力。[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)

MCP 协议仍在演进，实践时把所用协议版本和 SDK 版本写入项目说明，不混用不同年份教程的通信代码。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)

### 阶段七：作品集、面试与投递，20 小时

**目标：把学习成果转成可被招聘方核查的工程证据。**

学习与准备内容：

- 用一句话说明服务哪个用户、解决哪个问题、什么算成功。
- 讲清模型、网关、编排、工具、业务服务、知识库和状态存储的职责。
- 展示一项自己独立完成的改造及其前后效果，解释成本和局限。
- 练习现场修改工具参数、处理一个失败案例、说明一种设计取舍。
- 保持后端基础：数据结构、HTTP、数据库、并发、事务、缓存、消息和系统设计。

作品集至少包含：启动说明、架构图、数据与权限边界、评测方法、实际结果、失败案例、演示视频、自己完成的改造列表。

完成标准：能进行 10 分钟项目介绍，并承受 20 分钟追问；别人可以按说明复现核心演示；简历里的每个数字都有记录支持。

达到阶段四到五的主要标准后，就可以尝试投递匹配的应用岗位，再依据面试反馈补齐短板。阶段六可与投递并行推进。

## 6. 如何利用当前影院项目学透 Agent

### 6.1 当前源码确实有什么

优先阅读主目录 `cinema-ticketing-backend`；`内部agent/源文件` 中存在同名副本，阅读时注意区分。

关键文件：

- [Agent 主入口](E:/development/AI-Project/cinema-ticketing-backend/cinema-ai/app/main.py)
- [意图和参数理解](E:/development/AI-Project/cinema-ticketing-backend/cinema-ai/app/intent.py)
- [模型配置](E:/development/AI-Project/cinema-ticketing-backend/cinema-ai/app/model_config.py)
- [AI 网关](E:/development/AI-Project/cinema-ticketing-backend/cinema-ai-gateway/app/main.py)
- [项目说明](E:/development/AI-Project/README.md)

以本次读取的源码为准，注意五个事实：

1. `Assistant.chat()` 使用 `self.graph.ainvoke(state)`；`Assistant.live()` 手动依次调用意图、澄清、执行和校验节点，再流式生成回答。阅读实时链路时要跟 `live()`。
2. `_intent_node()` 将意图映射到指定工具。当前这条路径主要是模型理解加固定路由。
3. `_execute_node()` 调用注册工具的 `.ainvoke()`。`@tool` 装饰器本身不代表模型已经获得自由规划和多步骤执行能力。
4. `KeywordRetriever` 使用本地资料的关键词匹配，另有业务知识查询；后续可在此练习完整检索链路。
5. `_build_graph()` 中是 `graph.compile()`，这段代码没有配置持久检查点。不能只看框架名称就声称支持重启恢复。

默认聊天与转入内部 Agent 是不同路径：先从网关确认这次请求是否进入内部 `/ai/live`，再追踪 Agent 节点。这样能避免把 Dify 路径、`chat()` 路径和实时 `live()` 路径混在一起。

### 6.2 阅读代码的固定方法

每次只跟一个问题，例如：“我的订单 ABC123 能退吗？”

1. **输入**：问题、订单号、用户身份和历史从哪里来？
2. **判断**：意图如何产生，缺参数如何处理？
3. **执行**：调用了哪个函数，参数由谁构造？
4. **事实**：工具结果中哪些字段是权威业务结论？
5. **输出**：如何转成回答，失败和结束事件如何传给前端？

读不懂函数时，只记录“输入、输出、副作用、失败方式”四项。下一轮再深入内部实现。

### 6.3 把项目逐步变成求职作品

- **版本 A：解释清楚现状。** 补一页架构和调用链说明，建立最小评测集，明确哪些模块是原有代码。
- **版本 B：受约束工具循环。** 增加小型独立实验，支持多次只读查询、澄清、步骤上限与可追踪日志。
- **版本 C：有证据的 RAG。** 增加资料清洗、版本、混合检索或重排实验、引用与权限过滤，保留对比结果。
- **版本 D：可复用与可靠执行。** 封装只读 MCP 工具，补持久任务练习、人工确认和幂等机制。

每个版本都记录：问题是什么、自己改了什么、为什么这样选、结果如何、还存在哪些失败。

如果时间充足，可再做一个与后端经验贴近的小项目：**只读故障排查助手**。输入脱敏的模拟告警和日志，检索运维手册、调用只读诊断接口，输出证据、下一步建议和不确定项。这样能展示不同业务场景的迁移能力。

## 7. 未来更可能需要哪些能力

以下是结合当前职位样本和官方工程资料作出的学习优先级判断，**属于推断**。未来岗位数量、技术标准和具体工具的地位仍有不确定性。

### 第一层：优先持续积累

1. **业务验收与评测。** 自动化任务越复杂，越需要定义成功、保存轨迹并处理失败。练习把需求写成可检查的条件。
2. **上下文与数据治理。** 资料、历史和工具结果会持续增长，需要选择、压缩、更新、删除和权限隔离。练习让旧规则失效，让不同用户的数据保持隔离。
3. **工具与身份边界。** 能调用企业系统之后，参数校验、最小权限、操作确认和审计会更加关键。练习服务端注入身份和写操作授权。
4. **可靠的长任务执行。** 任务可能跨多个系统和时间段，需要状态持久化、取消、恢复和副作用控制。练习中断恢复和重复消息。
5. **质量、成本与延迟的共同优化。** 使用模型前后的数据证明取舍，练习模型路由、缓存失效和失败预算。
6. **行业理解和交付能力。** 从业务流程、数据可得性和验收要求出发，持续积累熟悉领域的真实问题。

这些判断分别受到现有平台/交付职位中的工程要求，以及上下文与持久化官方资料的支持；不意味着所有公司都要求同样的实现方式。[平台岗位样本](https://talent.baidu.com/jobs/detail/SOCIAL/75d3af47-7f79-4d71-862b-6fbca577bb19)、[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、[持久化机制](https://docs.langchain.com/oss/python/langgraph/persistence)

### 第二层：看场景再投入

- **多模态**：文档截图、图表、语音和视频。在确有这类输入的业务中，学习输入质量、延迟、成本及评测。
- **浏览器与桌面操作**：缺少接口的系统可能需要 UI 自动化；学习状态识别、失败恢复和操作授权。
- **多 Agent / A2A**：适用于可拆分或跨组织、跨系统的任务；先证明任务拆分有收益，再处理通信、重复工作和结果验收。
- **可复用技能与执行环境**：把领域知识、工具和流程形成可维护的能力单元，关注版本、依赖、权限和回归，而非只记某种目录格式。
- **用户体验**：让用户看懂正在做什么、何时需要补信息、如何取消或确认。后端工程师也需要理解这些交互约束。

### 第三层：作为专门职业方向

- Agent 训练、强化学习、模型对齐和训练数据工程。
- 高性能推理与 GPU 调度。
- 机器人、具身智能和物理环境控制。

对当前转岗目标，先完成核心路线，再根据具体 JD 决定上述分支。长期维护一个“岗位要求—已有证据—缺口”的清单，每月复查目标岗位即可。

## 8. 前 14 天：每天 30 分钟的起步安排

前两周合计 7 小时，主要用于理解现状并积累最小练习，不要求同时完成整套系统改造。遇到环境问题时将本日延续到下一天。

- **Day 01：追入口。** 找到 `/ai/live` 和 `Assistant.live()`，写出收到问题到发出回答的 5 个步骤。
- **Day 02：看结构。** 读 `intent.py` 的 `QuestionPlan`，解释 3 个字段；手写一个合法结果和一个非法结果。
- **Day 03：跟身份。** 跟一次查订单的 `user_id` 来源，写出用户输入与认证身份的区别。
- **Day 04：看工具。** 读 `create_tools()` 中一个查询函数，记录输入、输出、失败方式和 Java 接口。
- **Day 05：理解异步。** 找两个 `await` 和一个 `async for`，分别说明在等待什么；运行一个小型协程例子。
- **Day 06：看异常。** 阅读 `_execute_node()` 和 `_validate_node()`，写清超时、空结果和业务失败的不同处理。
- **Day 07：闭卷复述。** 不看代码，用 5 分钟讲一次查订单流程；剩余时间核对并改正。
- **Day 08：最小模型调用。** 查看模型配置，完成一次简单调用，记录返回文本和用量；密钥放环境配置中。
- **Day 09：结构化输出。** 让模型输出两个字段，再用 Pydantic 校验；记录一次不合格输出如何处理。
- **Day 10：模拟工具。** 写一个返回固定订单状态的普通函数，明确其参数及返回结构。
- **Day 11：工具调用前半程。** 给模型工具定义，观察它提出的名称和参数，先保存日志。
- **Day 12：工具调用后半程。** 执行模拟工具，把结果回传模型，取得最终回答。
- **Day 13：故障与边界。** 加一个缺参数案例和一个模拟超时案例，观察是否能澄清或结束。
- **Day 14：整理证据。** 保存 5 个案例与真实结果，写出“当前实现的路由方式”和“模型选工具”各自的一句话定义。

**今晚第一步**：只打开 `cinema-ai/app/main.py`，从 `live()` 开始跟“查我的订单”。半小时结束时，能讲清“问题进入哪里、工具由谁选、身份从哪里来、答案依据是什么”，就完成今天目标。

## 9. 面试与投递准备

### 9.1 你应该逐渐能回答的 15 个问题

1. 当前项目为什么采用固定路由？什么需求值得增加自主工具循环？
2. 模型输出 JSON 合法，为什么仍可能产生错误业务结果？
3. 工具名、参数和执行身份分别由谁决定？
4. 如何避免用户通过对话访问他人订单？
5. 模型和业务接口分别超时时如何处理？哪些失败可以重试？
6. `async/await`、消息队列和持久任务分别解决什么问题？
7. 工具已执行成功但响应丢失，重试如何避免重复副作用？
8. RAG 答错时，如何定位到清洗、切分、检索、重排或生成？
9. 退票政策变化后，如何更新索引、缓存和引用？
10. 历史对话、长期记忆和知识库如何区分？如何失效？
11. MCP 接入后，业务鉴权与授权放在哪里？
12. 为什么使用检查点仍可能重复执行外部操作？
13. 如何设计多轮评测、保留评测集和人工评分规则？
14. 如何降低成本，同时判断是否损害成功率？
15. 这个项目哪些是原有代码，哪些由你独立实现，有什么失败案例和证据？

### 9.2 简历如何写

使用“业务问题 + 自己的实现 + 验证方式 + 实际结果”的结构。例如：

> 在影院查询助手中独立实现……，通过……机制处理……问题；基于……条固定评测案例，将……从……改进到……，同时记录……方面的取舍。

省略号必须替换为真实工作和记录。无法量化时，写清实现边界和验收场景，也不要编造准确率、吞吐量或线上用户量。

准备四类材料：

- **运行证据**：别人能启动，或有完整演示与环境说明。
- **质量证据**：案例、评分方式、真实结果和版本对比。
- **设计证据**：至少 3 个取舍，例如固定路由与动态循环、关键词与向量、实时查询与缓存。
- **个人贡献证据**：提交记录、改造说明、问题复盘。

### 9.3 如何筛选岗位

搜索关键词可以从“Agent 应用开发”“大模型应用工程师”“AI 后端”“RAG 工程师”“Agent 平台”开始。

每周选 10 个与你城市、年限匹配的岗位，记录必需技能、加分项、业务场景和自己已有的证据。优先投递与你后端经验有交集的岗位，同时确认年限、学历、地点、语言、出差等约束。

如果岗位主要是训练、微调或强化学习，就按算法分支评估；如果主要是企业接口与任务流程，就用应用路线准备；如果主要是沙箱、调度和多租户，就用平台路线准备。
