## 二、上下文窗口与会话压缩

- 上下文窗口是模型单次处理可使用的信息预算，通常会包含系统和开发指令、对话、工具定义及工具返回内容，不只是用户输入的文字。
- 可用窗口大小取决于当前模型和运行环境；如果界面没有提供实时 token 用量或额度读数，就不应把某个具体数字当作当前会话的精确值。
- 会话接近上下文预算时，系统可能动态整理较早内容。整理通常优先保留当前目标、重要决定、约束、关键发现和待办事项；较早的逐字对话、大段工具输出或重复信息可能被摘要或省略。
- 压缩摘要便于继续工作，但不等于完整逐字记录；特别精确的代码、参数或引用，最好保存在项目文件中。

## 四、项目模块划分

按本次讨论采用的业务视角，项目分为六个模块：

1. **用户端**：注册登录、浏览影片和场次、查看座位、下单入口、订单及电影票查询、评论入口和 AI 助手入口。
2. **商家端**：影片、影院、影厅、座位和排期管理；订单查询、验票和退票规则维护等运营功能。项目现有管理界面主要以管理员后台实现。
3. **评论模块**：评分、影评、回复、点赞、举报和审核；评论资格需要结合用户是否有符合条件的观影记录判断。
4. **经营报表模块**：统计销售、订单、退票和上座率等经营数据，供管理端查询。
5. **下单真实业务模块**：锁座、创建订单、支付状态流转、取消、退票和出票。Redis 管理短期座位锁，MySQL 保存订单事实，RabbitMQ 和定时任务负责超时取消及补偿。项目支付流程应按当前实现描述为模拟/沙箱演示，不能说成已支持真实资金交易。
6. **AI 服务模块**：FastAPI 网关、LangGraph Agent、只读业务查询工具、知识检索、长期记忆及流式回复。用户端提供聊天入口，Agent 服务本身独立于票务交易逻辑。

这些模块共用 Spring Boot 业务接口及 MySQL、Redis、RabbitMQ 等基础设施；这里按业务职责划分，不代表每一项都是独立部署的服务。

## 五、项目最难的模块

建议回答：**下单与订单一致性是最难的模块。**

它要协调 Redis 座位锁、MySQL 订单状态和 RabbitMQ 超时取消。多人同时抢座、请求重试、锁过期、支付与取消同时发生时，都可能引起重复占座或状态错乱。项目通过 Redis Lua 原子锁座、创建订单时再次校验、请求和支付流水幂等、订单状态条件更新，以及超时取消和定时补偿来降低风险。

注意技术边界：Lua 能保证 Redis 内的检查和批量加锁原子执行，不代表 Redis 与 MySQL 之间存在跨系统事务；最终订单状态仍需数据库校验。

## 六、多人抢座：面试回答与追问

### 简单回答

我们以“场次 + 座位”作为锁的粒度。用户选座时，通过 Redis Lua 脚本一次性检查并锁定所选座位：全部可用才一起加锁，任何一个冲突就整批失败。锁设置 5 分钟过期；创建订单时再核对锁的持有人和数据库中的有效订单。请求使用幂等标识，超时未支付的订单由 RabbitMQ 延迟取消，并由定时任务补偿。Redis 处理短期并发占座，MySQL 保存订单最终状态。

### 常见追问

**为什么用 Lua？**

Redis 执行 Lua 脚本期间不会插入其他命令，所以检查一组座位和写入锁可以作为一个原子操作，避免部分座位锁成功、部分失败。

**拿到锁后创建订单失败怎么办？**

尽量按当前订单持有人释放锁；释放动作校验锁的持有人，防止误删后来用户的锁。异常情况下即使没有立即释放，锁也会在 TTL 到期后自动清理。

**锁过期时用户刚好支付怎么办？**

支付处理还要校验订单状态和座位归属。已超时关闭的订单不能直接继续出票，应进入退款或异常补偿流程；支付通知还要做幂等处理，避免重复出票。

**为什么不能只靠 Redis？**

Redis 锁用于快速处理并发竞争；订单和票项的最终状态保存在数据库，仍需事务、状态校验和幂等保护。Redis 锁本身不等于订单成功。
