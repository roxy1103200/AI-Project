# 管理端订单与影票详情查询模块实施方案

日期：2026-10-19（北京时间）。

本文为实施前制定的方案。现已补齐接口、页面和测试；实际交付、验证结果及尚未执行的验收项目见 [实现与验证记录](admin-order-query-implementation-2026-10-19.md)。本次没有数据库变更。

## 1. 模块定位与首版范围

新增「订单查询」模块，放入后台「票务服务」分组，入口为 `/admin/orders`。管理员输入完整订单号后，在同一页面查看订单、该订单下每张影票、支付、退款和异常核对信息。

一笔订单可以包含多张影票，所以查询结果采用「订单详情 + 影票明细」，不能将整笔订单等同于一张票。

首版包括：

- 按完整订单号精确查询，支持首尾空白清理、回车查询、清空结果和手动刷新。
- 查询所有本系统订单状态，覆盖未支付、已出票、已取消、退款中和已退款。
- 查看每张票的座位、成交单价、票项状态、验票时间和验票人员。
- 分别展示订单、支付、退款状态，并解释特殊组合。
- 展示本地最近核对结果、异常原因、上次检查与下次计划检查时间。
- 跳转既有验票和支付核对模块；验票入口预填当前订单号。
- 兼容历史模拟支付和支付宝沙箱支付。

首版以只读查询为边界：刷新不触发支付宝查单、不触发退款重试，不修改订单和座位。人工确认未付款后取消异常订单属于独立的后续写操作方案，不混入本次查询模块。

## 2. 当前实现与复用判断

### 2.1 已有能力

- `TicketCheckInAdmin.tsx`、`GET /api/admin/tickets/{orderNo}`：已支持管理员按订单号查票，但返回内容主要服务验票，缺少金额、完整支付及退款信息。
- `OrderReadService.find(userId, orderNo)`：提供用户范围内的订单与退票资格，网站和内部 Agent 已复用。
- `OrderStatusSummary`：统一订单、支付和退款组合状态以及当前退票资格说明。
- `PaymentAdmin.tsx`、`GET /api/admin/payments/exceptions`：提供异常列表，缺少按任意订单号查询的完整详情。
- `PaymentStore`：已有支付单、退款单、核对时间、错误码及补偿退款记录。
- `ADMIN_PAGES`、`AdminWorkspace`：已有统一侧栏、手机导航和模块分发机制。

### 2.2 新增而非直接放宽用户接口

新增管理员专用聚合接口。保留用户查询接口的订单归属限制，不给 `OrderReadService.find` 增加「userId 为空就查看任何订单」之类隐式放权分支。

共享 `OrderStatusSummary` 的状态解释。验票时段、已验票和退款资格判断复用后端业务规则；新页面只展示后端计算结果，不自己根据时间和状态猜测可操作性。

## 3. 页面设计

### 3.1 查询区

标题：订单查询。

说明：按订单号查看订单、电影票及支付退款记录。

输入框旁放置「查询」「清空」。查到记录后出现「刷新记录」；按钮说明刷新的是本系统已记录的信息。查询前不加载全量订单、影片、影院或用户列表。

交互要求：

- 初始状态显示输入提示，不显示空白详情卡片。
- 空字符串、仅空白或超过 64 字符时就地提示，不发送请求。
- 查询 A 后开始查询 B，清除旧结果或明确遮罩为加载状态，不能将 A 的信息误认成 B。
- 使用 AbortController 和请求序号处理并发；A 的迟到响应不能覆盖 B。
- 输入已改动但尚未查询时，详情明确标注当前展示的原订单号，相关跳转始终取已查询结果。
- 未找到显示「未找到该订单，请核对完整订单号」，不将权限或网络错误显示为不存在。

### 3.2 概览区

展示订单号、影片、影院/影厅、开场时间、订单金额、影票张数和购票人账号。

订单状态、支付状态、退款状态分别展示。关单中、退款待核对和迟到付款补偿提供明显的文字说明；颜色只作辅助。

金额旁保留支付渠道与环境，例如「支付宝 · 沙箱」「历史模拟支付」。未付款、尚未创建支付单时，渠道显示「未发起」，不要虚构支付宝交易。

### 3.3 详情分区

桌面采用主内容与辅助信息两栏，手机单列展开，沿用现有管理后台颜色、字体和按钮组件：

1. **订单与场次**：创建时间、支付截止、影院影厅、影片时长、放映结束时间、场次当前状态。
2. **电影票明细**：每张票独立一行，显示座位编号、成交单价、票项状态和验票信息；最多 6 张，完整展示。
3. **支付记录**：本地支付单状态、商户支付单号、渠道交易号、收款记录、支付与本地确认时间。
4. **退款记录**：原退款流水号、金额、原因、普通退票/迟到付款补偿、状态、规则版本和核对进度。
5. **当前服务资格**：能否验票、能否申请退票及原因，标明依据当前规则和服务器时间计算。
6. **异常核对**：错误说明、最近核对时间、下次计划检查时间、配置匹配情况；原始错误码放入展开详情。
7. **已记录事件**：展示有真实时间字段支持的事件；不宣称完整操作审计。

首版用座位编号清单表达影票，不强依赖全厅座位图。未来补座位图时，需新增受管理员鉴权的读取入口，明确它展示当前布局；现有用户座位图接口不能直接用于跨用户查询，也没有完整历史布局快照保证。

### 3.4 跳转与深链接

- 模块入口：`/admin/orders`。
- 定位订单：`/admin/orders?orderNo=<编码后的订单号>`。
- 验票入口：`/admin/ticket-check-in?orderNo=<编码后的订单号>`，预填后读取现有查票接口；实际验票仍由原按钮显式提交。
- 支付核对：进入既有 `/admin/payments`；首版不承诺已有页面支持按订单号自动筛选。

必须一起处理当前路由的细节：`App.navigate(next)` 现在将包含查询串的完整 next 放进 path，而 `adminView` 按纯路径匹配。应分开保存 pathname 与 search，pushState、popstate 和同路径查询串变化均同步更新，再把解析后的 orderNo 作为显式参数传入页面。只调用 navigate 携带参数、却不处理路由，会落入「管理页面不存在」。

普通用户和未登录用户通过深链接访问时仍先经过原管理端访问控制；登录成功后，按其真实角色决定是否可继续查看。

## 4. 查询数据与来源

### 4.1 订单与场次

从 `ticket_order` 读取订单号、用户、场次、成交金额、订单状态、创建时间、到期时间和收款时间。

关联 `screening`、`movie`、`hall`、`cinema` 读取展示资料。影片下线、归档和场次过期不应让历史订单消失；不套用观众端「当前可售场次」过滤。

当前场次和影片资料会变化，首版须将其视为当前关联资料。数据库没有保存的购票时影片标题或完整场次快照，不包装成不可变历史事实。

购票人仅返回必要的用户 ID 与账号名称，默认不返回手机号。验票人员通过账号 ID 关联名称，缺失时展示 ID 或「历史账号」，不丢失验票时间。

### 4.2 影票

从 `order_item` 和 `seat` 读取票项 ID、座位 ID、座位编号、成交单价、票项状态、验票时间及人员。

单价以 `order_item.price` 为准，不用当前场次价格替换。保留历史 `VALID` 的兼容展示。每张票的验票状态独立展示，整单不应因其中一张已验票而显示成全部已验票。

### 4.3 支付与退款

- `payment_order`：支付状态、渠道/环境、out_trade_no、channel_trade_no、截止时间、发放收银台时间、关单申请时间/原因、错误码及核对计划。
- `payment_transaction`：已确认收款记录，保留历史 MOCK 的渠道和环境。
- `refund_record`：退款记录列表，含 reason_type、policy_version、attempts、requested_at、refunded_at、last_error_code、next_check_at。

缺少 `payment_order` 但存在历史模拟收款流水时，应显示模拟支付成功；不能因为没有支付宝支付单就显示未支付。

多张票、收款和退款分开读取，不将多个一对多关系拼成一条 SQL 再累计金额，避免重复显示及金额放大。

### 4.4 事件时间的边界

允许展示的事件包括创建、收银台入口已发放、申请关单、渠道付款、本地确认收款、申请退款、确认退款和逐票验票。

- `expire_at` 是截止时间，不是实际取消时间。
- `close_requested_at` 是申请时间，不是关单完成时间。
- 当前没有完整 `cancelled_at`、`issued_at` 字段，缺失时明确未记录。
- checkout_issued_at 只表示本地发放过收银台页面，不证明客户打开成功，更不证明已付款。
- 时间未知的历史退款记录仍展示，不拿创建时间冒充成功时间。

## 5. 状态解释与异常判定

状态解释优先由共享的 `OrderStatusSummary` 产生；管理员诊断补充独立字段，不修改用户端和 Agent 的只读边界。

- `UNPAID + NOT_STARTED`：未支付，尚未发起支付。
- `UNPAID + INIT/PAYING`：尚未确认收款；不能据此断言渠道没有扣款。
- `UNPAID + CLOSING`：关单处理中，尚未确认取消，仍可能占座。
- `ISSUED + SUCCESS`：支付已确认，影票按各自验票状态展示。
- `REFUNDING + PENDING/UNKNOWN`：退款处理中或结果待核对，影票暂不可使用。
- `REFUNDED`：本系统已确认退款，票项失效。
- `CANCELLED + 无收款事实`：本地已取消；同时存在渠道核对异常时仍提示核对情况。
- `CANCELLED + SUCCESS + LATE_PAYMENT`：分别展示取消事实和补偿退款进度，不能简化成「无需退款」。

同一订单的不同状态出现不符合既有状态机的组合时，展示数据异常提示和原始状态，不自行修正状态。

错误提示建议：

- CONFIG_MISMATCH：支付单所属应用或商户配置与当前服务不一致，需要管理员核对；刷新记录无法修复。
- CHANNEL_UNAVAILABLE：渠道连接或响应异常，查看后台最近核对情况。
- CLOSED_WITH_PAYMENT_REVIEW：交易关闭同时存在付款信息，需要人工核对收款与退款。
- LOCAL_RECONCILE_FAILED：本地处理失败，需要结合 traceId 和日志排查。
- 退款已尝试 8 次、状态仍 UNKNOWN 且没有后续计划：自动核对已暂停，前往支付与退款核对模块处理。

支付关单当前没有退款同样的 8 次上限，不显示「支付重试已耗尽」等不存在的结论。next_check_at 是计划时间，不是保证执行时间。

配置诊断仅对支付宝在途支付适用。通过与实际注入的 PaymentProperties 对比，返回 MATCH/MISMATCH/UNKNOWN；应用和商户标识只显示脱敏尾号。缺配置显示 UNKNOWN；历史已结算支付单与当前配置不同，不自动认定为新的故障。

## 6. 后端接口与实现

### 6.1 新增只读接口

`GET /api/admin/orders/{orderNo}`

使用既有 `X-Auth-Token` 和 `ApiResponse`。Controller 首先调用 `AuthService.requireAdmin(token)`，再执行查询。

输入规则：去除首尾空白，非空且不超过现有列长度 64；采用参数化 SQL 按订单号等值查询。保留历史订单号兼容性，不额外要求 UUID，也不改成默认模糊搜索。

响应：401 登录失效；403 非管理员；400 输入不合法；404 主订单不存在；503/500 按既有异常约定区分服务不可用和内部失败。不得把数据库故障伪装成 404。

### 6.2 目标响应结构

采用显式 DTO，统一 camelCase，建议命名 `AdminOrderDetail`，包含：

- order：订单号、状态、金额字符串、时间和张数。
- customer：用户 ID、账号名称。
- screening：影片、影院、影厅、开场/放映结束、场次状态。
- tickets：逐张影票、座位、单价、状态与验票信息。
- payment：可空，本地支付单与核对信息。
- receipts：收款流水列表，兼容历史模拟记录。
- refunds：退款记录列表，允许为空。
- eligibility：canCheckIn、checkInReason、canRefund、refundDeadline、refundReason。
- diagnostics：异常代码、可读说明、严重程度、配置匹配情况及脱敏标识。
- events：有真实证据时间的事件及其来源类型。
- serverTime、timeZone、dataWarnings。

金额后端使用 BigDecimal，新接口输出如 `"52.00"`，前端不自行用浮点累计交易金额。

先通过 JdbcTimes 统一 JDBC 时间类型，再明确按 Asia/Shanghai 输出带 `+08:00` 的 ISO 8601 时间；只约束这个新增 DTO，不顺带改变现有用户接口的序列化格式。界面统一标记北京时间。

### 6.3 聚合查询策略

新增 `AdminOrderQueryController`、`AdminOrderQueryService` 和 DTO。服务方法采用只读、REPEATABLE_READ 本地事务，保证订单、票项、收款和退款多次 SELECT 来自同一个数据库快照。

以 order_no 唯一索引定位主订单，然后按 order_id 读取票项、支付和退款；首版无需新增索引或数据表。用 EXPLAIN 核对订单号索引与子表外键索引的使用。

对必要关联资料采用显式缺失处理。主订单存在但历史附属资料缺失时，保留主订单并给出 dataWarnings；查无收款、退款或通知记录属于正常空结果，不导致整个详情失败。

验票资格建议将 TicketCheckInService 中可复用的纯判定规则提取为策略方法，供原入口和新查询共用；原写接口继续在事务内重新校验，不信任前端展示的资格。

资格判断以同一份服务器时间计算。API 返回本地已知快照，不承诺支付宝实时状态；读取不调用 PaymentService.synchronize、reconcile、refund，也不领取租约或释放 Redis 锁。

### 6.4 权限、数据最小化与缓存

- 沿用现有全局 ADMIN 模型，不新增影院级角色。
- 后端鉴权覆盖所有详情，普通用户即使知道订单号也不可调用。
- 不返回密码哈希、lock_owner、登录 Token、checkout_token_hash、签名正文、密钥文件路径和租约令牌。
- 响应使用 Cache-Control: no-store；前端不把详情写入 localStorage。
- 复用 useScopedRequest，登出、换号或权限失效时取消在途请求并清空详情。
- 日志保留 traceId、操作管理员 ID 和目标订单 ID，避免输出完整支付报文、联系方式和密钥。
- 查询不写 payment_operation_log；该表目前面向退款操作且 refund_id 必填，不适合作为查单审计表硬复用。

- 新增 `src/admin/order-query.css`：沿用后台设计系统，桌面分区、手机单列、长流水号换行。

复制订单号等操作只在用户点击时进行；剪贴板不可用时提供可选中文本。保留表单 label、加载 role=status、异常 role=alert 和可见键盘焦点。

## 8. 与已有模块的边界

- **用户与权限模块**：提供管理员身份，保持普通用户只能读取本人订单。
- **订单模块**：提供成交事实和票项，不增加修改状态入口。
- **支付模块**：提供本地收款、关单和异常证据；查询页面不推进资金状态。
- **退款模块**：展示状态、补偿原因和核对进度；重试仍在既有受控入口执行。
- **验票模块**：查看详情可跳转，实际验票仍由原流程提交。
- **Agent 模块**：本次不增加管理员 MCP 工具，不把后台跨用户查询能力开放给模型。
- **经营报表**：沿用实际流水口径，不把当前订单金额等同于已收款净额。

## 9. 实施顺序

### 阶段一：冻结协议与状态口径

确定 DTO、金额时间格式、三类状态标签、缺失字段行为和异常说明；准备独立测试数据，包含普通订单、关单异常及迟到付款补偿。

### 阶段二：实现后端只读聚合

先完成管理员鉴权、精确查询、票项与资金记录读取、资格复用及 DTO 白名单；验证查询没有业务写入和外部渠道调用。

### 阶段三：实现页面与导航

完成路由参数处理、查询表单、详情区、错误状态及验票跳转。保持既有管理导航和用户购票路径不变。

### 阶段四：隔离验证

运行以下 36 个测试点；涉及支付状态的样例通过隔离库或测试替身构造，不在真实订单上批量制造支付、取消和退款。

### 阶段五：发布与回退

交付后端构建、前端 dist 和接口文档；部署先更新后端再更新前端。服务器尚无新接口时显示明确的版本/服务错误，不回退调用用户接口越权查询。

首版无数据库迁移，回退前后端构建即可。服务重启、原站登录验证和部署作为独立发布动作安排，本方案没有执行。

## 10. 验收清单：36 个测试点

### A. 身份与输入

- [ ] A01：未登录查询返回 401，页面不残留上一个账号的详情。
- [ ] A02：普通用户即使提供正确订单号也返回 403。
- [ ] A03：管理员可以查询另一用户的订单，且没有伪造用户登录或修改订单归属。
- [ ] A04：被撤销或降权的管理员旧会话不再能读取详情。
- [ ] A05：空白、超长输入被拒绝，首尾空格正常去除，特殊字符不能改变查询 SQL。
- [ ] A06：格式可接受但不存在的完整订单号返回 404，网络/数据库故障不伪装成不存在。

### B. 基础订单与影票

- [ ] B01：未支付且未发起支付的订单正常展示，没有虚构渠道交易。
- [ ] B02：已出票的多座订单逐票展示，成交单价和总额正确，不因 JOIN 重复影票。
- [ ] B03：部分票已验票时准确区分逐票状态，保留首次验票人员和时间。
- [ ] B04：已取消未收款订单保留明细，不能误显示可以验票。
- [ ] B05：普通已退款订单显示退款证据和失效票项，不显示已出票可用。
- [ ] B06：影片已下线或归档、场次已过期的历史订单仍可查询。

### C. 复杂状态

- [ ] C01：UNPAID + CLOSING 显示尚未确认取消，不宣称已释放座位。
- [ ] C02：REFUNDING + PENDING 显示退款处理中，影票暂不可用。
- [ ] C03：REFUNDING + UNKNOWN 不宣称退款失败或已到账。
- [ ] C04：CANCELLED + SUCCESS + LATE_PAYMENT + 待退款同时展示取消和收款补偿。
- [ ] C05：迟到付款补偿已 REFUNDED 时显示已确认，不再建议客户重复申请。
- [ ] C06：未知或不符合状态机的组合显示原始状态和核对提示，不自动修正。

### D. 支付兼容与异常诊断

- [ ] D01：CONFIG_MISMATCH 显示脱敏身份及异常说明，查询不修改 APPID。
- [ ] D02：无 payment_order 的历史模拟收款记录仍显示 MOCK 成功。
- [ ] D03：渠道异常记录仅展示最近已知信息，读取不会实际发出查单或关单请求。
- [ ] D04：不存在退款记录返回空列表；存在多条历史记录时分别展示，不放大金额。
- [ ] D05：退款 UNKNOWN 且自动尝试耗尽时提示前往核对模块；支付关单不套用 8 次上限。
- [ ] D06：配置缺失返回 UNKNOWN；历史已关闭订单配置不同不被误报成当前在途故障。

### E. 前端交互与路由

- [ ] E01：按钮与回车均可查询，刷新使用当前已查询订单号，输入变化不会误操作旧结果。
- [ ] E02：A、B 连续查询且 A 较晚返回时，最终只展示 B。
- [ ] E03：切换模块、登出或换号时中止旧请求，详情与错误提示正确清理。
- [ ] E04：复制在用户点击后发生，剪贴板不可用时提供可选中文本。
- [ ] E05：直接深链接、同路径更换 orderNo、浏览器前进后退，以及跳转验票预填均正确。
- [ ] E06：320px 手机及桌面无横向溢出，长流水号可换行，键盘可完成查询和查看详情。

### F. 一致性与数据边界

- [ ] F01：并发支付或退款变更时，单次详情来自一个数据库读取快照。
- [ ] F02：查询和刷新不执行订单/支付/退款写入、租约领取或 Redis 锁释放。
- [ ] F03：金额保持小数精度，TIMESTAMP 与 DATETIME 正确转换，界面显示北京时间。
- [ ] F04：主订单存在但附属历史资料缺失时返回主订单和提示，不误报主订单不存在。
- [ ] F05：完整订单号命中唯一索引；首屏不读取全量用户、影片、影院或订单。
- [ ] F06：事件只使用实际记录时间，不把到期时间、关单申请或收银台发放解释为取消、支付成功。

## 11. 交付标准与后续扩展

交付：管理员查询接口与 DTO、独立后台页面、导航与深链接、验票预填、对应测试及接口说明。36 项逐项记录通过、失败、未执行或阻塞，不能用构建通过替代状态和权限验收。

后续可独立规划：按日期/用户筛选订单、管理员受控主动查渠道、核实未付款后的异常关单恢复、完整操作审计及历史场次布局快照。特别是异常关单恢复，需要渠道证据、权限、并发幂等和迟到付款补偿设计，不能从首版查询页面直接修改数据库状态。
