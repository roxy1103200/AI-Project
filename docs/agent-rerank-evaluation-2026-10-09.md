# Rerank 新评测（2026-10-09）

## 结论

新增重排已真实生效：本轮合计 **30/30 次原生云端重排成功、0 回退、usage 无缺失**。小规模规则证据专项的首位命中率由 **90% 提升至 100%**，但没有证据表明端到端任务成功率提高。

同版代码、同一知识内容，只改变重排开关的 96 次 Agent 对照中，严格成功率为关闭 **77.1%（37/48）**、开启 **75.0%（36/48）**。7 对结果不同的任务均未触发规则重排，不能把这一个任务的差距归因于 rerank；真正经过规则检索的子集两版均为 **4/6 成功**。

应优先处理规则数据一致性和数据库知识召回，再评估更大候选集上的重排效果。

## 设计与范围

- 端到端：原有 24 道真实业务题，每版 2 轮，共 96 次；使用本轮重新冻结的开发业务快照。
- 对照：**同一份当前工作区代码**，一份 `RERANK_ENABLED=false`，一份为 `true`。不是用更早的固定工具流程作基线，也没有将候选切片、并行读取和知识正文变化混为开关收益。
- 当前 HEAD 为 `f289f4a`，rerank 业务改动尚未提交；实际工作区的 Python 源码和知识文档副本及 SHA256 已保留在 `measured-source/` 与 `metadata.json`。
- 规则证据专项：12 个自然语言问题，其中 10 个有答案、2 个无答案；两版各重复 2 次，共 48 次排序测量。候选来自真实本地和 Java 检索并提前冻结，没有加入人工干扰文档。
- 专项直接比较候选排序，不经过 Agent 意图识别，不生成最终回答；不能把专项命中率叫作 Agent 问答准确率。
- 并发 1，新旧顺序交替。Qwen3.7 Flash、温度 0、输出上限 2048、关闭思考和记忆、工具尝试预算 4。原生重排使用 `qwen3.7-text-rerank`，Top K=30、Top N=4、超时 5 秒。
- 端到端计时完成后再执行云端排序专项，避免并发外部请求干扰端到端耗时。

- 候选召回覆盖：100% → 100%。
- **首位证据命中：18/20（90%）→ 20/20（100%）**。
- 前 4 证据覆盖：100% → 100%。
- **MRR：0.950 → 1.000**。
- NDCG@4：0.963 → 1.000；二元相关性，候选缺失按 0 分计。
- 来源映射、原文与 chunk ID 保留检查：两版均 24/24 正确，包含无答案题。

## 为什么还没带来回答收益

### 1. 实时规则接口自身有冲突

本轮 Java `/internal/refund-policy` 实际返回：

```json
{
  "policy": "仅支持开场前 30 分钟完成退票，已出票订单可申请退票。",
  "cutoff_minutes": 5
}
```

纯规则题两版两轮均回答 30 分钟。重排后的本地片段本身未写 30 分钟，最终模型仍受到独立 `policy` 正文影响。该 `policy` 字段不参与重排，因此仅调相关性排序解决不了这处矛盾。

代码依据：`InternalAiController.refundPolicy` 同时读取数据库 `content` 和 `cutoff_minutes`；`OrderService` 实际用数值字段校验截止。应统一发布规则正文与参数，并在冲突时明确结构化实时字段的优先级。

### 2. 真实数据库知识没有被这些自然语言问题召回

专项 12 个自然语言问题的 Java 知识搜索结果全部为空；排序候选实际只有本地 Markdown 的 2～3 段。`InternalAiController.knowledgeSearch` 对**完整问题**做 `LIKE '%完整问题%'`，不会自动提取关键词或做语义召回。

单独用“退票规则”“购票”等短词可查到已发布数据库文档，但自然语言问题通常无法完整匹配。应先改进关键词提取或召回方式，再验证数据库候选的重排收益。

### 3. Top N 大于本轮候选数

本轮候选 2～3 段，Top N=4，关闭和开启都保留全部候选。rerank 主要改变顺序，还增加 `rerank_score` 等元数据；没有减少交给模型的片段数量，不能期待仅靠此次开关降低上下文 Token。

### 4. Agent 规划仍有波动

S04/S05 有多余座位查询；S11 有推荐后的多余调用与预算耗尽；S12 有无效重试；M04 有一次误追问；M06 有参数约束/预算问题。这些问题与规则重排无直接关联。
