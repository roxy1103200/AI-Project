- 日期：2026-10-17。
- 状态：待实施。本文件是开发及验收清单，不代表代码已修复或测试已通过。
- 项目根目录：`E:\development\AI-Project`。下文代码路径均相对于该目录。
- 对象：网站“智能 Agent”入口及内部 Agent；本轮不涉及 Dify 工作流改造。
- 核心复现：用户说“给我推荐最近一周的电影”，系统却先追问“新上映的，还是有可购票场次的”。

## 1. 本轮要解决的问题

推荐任务允许采用可解释、可纠正的默认理解。对于“给我推荐最近一周的电影”，首轮按最近 7 天上映的影片查询，说明实际起止日期并给出结果。

参考日为北京时间 **2026-10-17** 时，期望答复形式为：

> 我先按最近 7 天上映的影片为你推荐，范围是 2026-10-11 至 2026-10-17（北京时间，含起止日）。
>
> 以下根据查询结果列出片名、题材及上映日期。

示例中的影片必须来自业务查询；无结果时直接说明无结果。默认理解不能写成“用户已确认”，也不能先追问类型、城市、影院后才开始推荐。

### 1.1 已定位的链路证据

- 提问：`给我推荐最近一周的电影`。
- 发生时间：2026-10-17 22:50:52，Asia/Shanghai。
- Trace ID：`b0447d95-0c2f-40ee-af8c-e83e1979e54a`。
- Request ID：`d5a60e8a4bf94591a3f2708a72b72a59`。
- Message ID：`8007ae11-fc2b-4860-b07a-4ad0c970ef99`。
- 本地追踪：`langsmith(tracing)/2026_10_17/8_2026_10_17_22_50_858055ae9ebf/traces.jsonl`。
- 实际路径：`prepare → clarify → respond`。
- 实际意图：`recommend`。
- 拦截原因：`preflight_reason=ambiguous_time_target`。
- 时间状态：`target=unspecified`、`status=ambiguous`、`reason=target_required`。
- 模型调用：0 次；业务工具调用：0 次。

这次追问由代码预检触发。修改模型提示词不能单独解决此问题。

### 1.2 当前代码中的四个直接原因

1. `app/intent.py` 的 `rule_plan()` 在未识别时间对象时，传入 `default_target="unspecified"`。
2. `app/intent_routing.py` 的 `preliminary_route()` 在模型理解前检查时间，直接把上述状态转为澄清。
3. `app/intent.py` 的 `understand()` 在最终处理时再次调用 `normalize_times(..., "unspecified")`。只改前面的默认值，会被这里覆盖。
4. `grounded_time_query` 对推荐路径要求非空题材偏好。即使时间已解决，不指定题材的推荐仍可能进入额外理解路径。

另有两处配套问题：

- `app/query_answers.py` 把 `assumed_target=true` 的默认理解写成“已确认”。
- `time_target_choice()` 只在上一轮助手出现固定二选一问句时识别对象选择；直接推荐以后，用户纠正时间含义也必须生效。

## 2. 产品语义与范围

### 2.1 首轮处理原则

按以下次序处理，不采用“发现任何歧义就追问”的统一策略：

1. **日期无效、范围倒置或无法同时满足的硬性日期冲突**：先澄清，不发出带错误条件的业务查询。
2. **用户明确说明时间对象**：按“上映/首映”或“场次/有票/观影”等实际语义处理。
3. **当前是对上一轮条件的修改**：继承有效上下文，只修改本轮明确改变的部分。
4. **明确推荐意图 + 最近一周/最近 7 天 + 未说明时间对象**：默认按上映日期理解，直接推荐，并披露默认口径。
5. **其他缺少必要条件的请求**：只询问完成当前任务真正需要的信息。

第一版默认策略限定在上述明确的“最近一周/最近 7 天”推荐表达及等价口语，不把所有带时间的请求都默认成上映日期。

### 2.2 必须确定的业务约定

- “最近一周”及“最近 7 天”：含参考当天，向前共 7 个自然日。
- “本周/这周”：北京时间周一至周日，不等于滚动最近 7 天。
- “最好/优先/尽量是最近一周”：日期为软偏好；范围外补充项必须单独标注。
- “最近一周”未带软化词，或带“只要/仅限/必须”：日期为硬条件。
- 用户未提供题材：`preference=""`，不能编造一个题材。
- 用户明确提供题材：保留原题材，不允许模型用“最近一周”替换它。
- 仅按上映日期推荐：查询影片目录，不额外增加有场次、可购票、城市或影院条件。
- 用户说“有票/能买”：查询当前可订购条件；用户说“排期/场次安排”：保留 scheduled 语义，不能自动改成 bookable。
- 推荐不等于保证可购票。回答中不能把上映日期写成观影日期。

### 2.3 本轮保留的必要澄清

以下问题仍允许或要求澄清：

- `这周的悬疑题材电影有哪部`：没有明确推荐意图，保留当前上映/观影对象澄清策略。
- `推荐下周的电影`：既未说明上映，也未说明观影，且不属于本轮“最近 7 天”默认范围。
- `2026年2月30日有哪些场次`：日期不存在。
- `只要2026年10月11日至17日上映，同时必须2026年10月18日至24日上映的电影`：同一上映对象的硬条件冲突。
- `查一下座位`：没有场次或足够的影片、影院、日期信息。
- `我的订单能退吗`：缺少当前接口必要的订单标识，不能猜测本人订单。

“没有结果”与“缺少必要条件”要分开：参数完整但结果为空时，应答复空结果。

## 6. 自动断言与证据要求

### 6.1 每个直接推荐场景至少断言

- 意图及任务正确，`clarification` 为空。
- 时间对象、参考日期、起止日期、软硬条件、`assumed_target` 正确。
- 前后两次处理没有把时间对象改回 `unspecified`。
- 业务工具参数与已验证条件一致，Java 实际接收条件相同。

- SSE 结束状态及网关历史一致。

不能仅以“答案含片名”或“HTTP 200”判定通过。语义等价措辞可接受，不把整段答案逐字相等作为主要评分方式。

日期预期从测试参考时钟独立计算，影片预期从夹具事实快照独立筛选。评分器不能调用被测时间决策函数计算自己的预期，否则同一个错误可能同时出现在执行与评分中。

### 6.3 结果文件

沿用现有 `preflight.json`、`fixture-snapshot.json`、`trials.json`、`summary.json`；在 v2 中补充套件版本、默认策略版本及新增断言结果。

- 测试编号、原始测试问题、会话测试别名、参考时间和时区。
- 时间摘要、规范化工具参数、Java 查询证据、事实快照。
- 最终答案、终止类型、澄清原因、错误代码。

### 状态口径
