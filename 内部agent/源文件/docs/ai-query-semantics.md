# 内部 Agent 影片与排期查询规则

## 业务口径

- **影片资料（catalog）**：查询未下线影片的基础资料，不能证明有排期。
- **上映中（showing）**：当前影片状态为 `ON_SHELF` 或兼容旧数据的 `ON_SHOW`，且上映日期不晚于查询日期。上映日期为空时沿用声明状态。这个范围不要求有场次，也不使用开售时间判断上映。
- **已排期（scheduled）**：必须存在真实的 `SCHEDULED` 场次，影院和影厅均为 `ACTIVE`，影片未下线。包括未上映、未开售、当天已经开场的有效排期；排除已取消场次。
- **可订购（bookable）**：沿用现有售票规则，额外要求未开场、在影片开售窗口内等。没有可订购场次，不能推导出没有排期。
- **上映且有排期**：使用 `scheduled` 并显式设置 `showing_only=true`；普通排期查询不自动附加上映条件。

当前没有影片状态历史表，按历史日期查询“上映中”仍基于当前状态与上映日期，不能重建历史上架/下架过程。

## 日期与追问

1. Agent 在一次理解请求中固定北京时间日期。`今天/今日` 对应当天；`明天/后天` 按该日期偏移。明确日期和业务范围会覆盖模型的提取结果，模型不能删除、替换日期，或者自行切换为上映列表。
2. Java 使用 `Asia/Shanghai` 业务时钟。指定日期按开场时间的 `[当天 00:00, 次日 00:00)` 筛选，包含当天已开场的有效排期。
3. 排期未指定日期时查询北京时间今天及以后，并在回答中注明范围，不由模型猜日期。
4. 支持具体日期、月日、相对日期、星期、周末、月份和年份范围，以及“明天到后天”这类区间。`本周三` 为本周的周三，`下周一` 为下一周周一，单独 `周三` 为今天或之后最近的周三。范围直接转换为起止日期；无效、年份存在歧义、多个冲突范围先澄清，不执行去掉日期条件后的宽泛查询。
5. “那明天呢”“那后天呢”“第2页”“下一页”承接前一轮查询类型与明确片名。新的全量列表问题不沿用上一轮片名。
6. “今天有哪些电影”没有说明上映或排期，会先询问查询范围。
7. `最近一周/近7天/过去一周` 是含今天的近 7 个自然日；`未来一周` 是今天起的 7 个自然日。`上周/下周` 为对应自然周的周一至周日。影片推荐中的本周、本月、今年上映，截止到当前业务日期；明确查询未来上映则保留未来范围。
8. 上映日期范围使用 `release_date_from/to`，场次日期范围使用 `screening_date_from/to`。单日场次保留兼容字段 `screening_date`。上午为 `[00:00,12:00)`，下午为 `[12:00,18:00)`，晚上为 `[18:00,24:00)`，使用 `screening_hour_from/to` 查询并在回复中说明。
9. “推荐电影并给出明确时间信息”仍为推荐任务，“时间”单独出现不触发场次查询。未明确时间对象的近期电影推荐，默认解释为上映日期并在回复中说明。明确“明晚能看的电影”则查询具有符合日期和时段的可订购场次的影片。
10. “最好、优先、尽量”是软性上映日期偏好，范围内影片优先排列，范围外补充逐一标注；“必须、只要、仅限”是硬条件。推荐接口在数据库筛选或排序后再取前 5 部，不能先取少量候选再过滤。
11. “最近/过几天”没有明确长度时保留歧义。精确查询要求补充范围；“最好最近上映”可先按上映日期由近到远推荐，并说明未限定具体范围。未收录上映日期的影片不能作为满足硬性上映日期条件的结果。
12. 时间追问继承已确认的影片、任务类型和早晚时段，替换本轮提供的日期；相对表达始终以本轮固定北京时间重新计算。新全量查询不继承上一轮片名。多个不同影片分别绑定不同日期、离散的多段日期或时段暂不展开为多组工具任务，会先要求用户确认对应范围。

## 查询链路

明确的全量列表问题走确定规则 → MCP → Java → MySQL → 结果校验 → 固定事实回答。

片名/影院等自由表达仍可以通过模型提取，随后受固定业务范围、用户提供的实体和日期约束。影片和场次结果直接生成回答，不经过模型重新解释，也不检索长期记忆作为实时业务依据。推荐及其他业务保留原链路。

排期电影查询先用 `EXISTS` 筛选有实际场次的电影，再按电影分页和去重，不从前 50 个场次推导全部影片。每页默认 20 部、最多 50 部，返回电影总数、页码和是否有后续页。

场次计数和摘要分批查询，避免逐片请求数据库。每部电影最多展示 10 个场次摘要，整页摘要读取上限 2000 条；计数仍来自独立聚合。摘要未完整展示时明确提示。独立场次明细接口仍最多返回 50 条，回答显示前 12 条并提示限制。

## MCP 与 Java 接口

MCP 保留原有四个只读工具，扩展以下参数：

- `search_movies`：新增 `movie_scope=catalog|showing|scheduled`、`screening_date`、`cinema_query`、`showing_only`、`page`、`page_size`。日期格式为 `YYYY-MM-DD`。
- `search_screenings`：新增 `query_scope=scheduled|bookable` 和 `showing_only`。
- 两项查询均支持场次日期起止范围及上午、下午、晚上时段；`search_movies` 额外支持上映日期起止范围。参数使用下划线形式，MCP 转为 Java 的 `screeningDateFrom/To`、`screeningHourFrom/To` 和 `releaseDateFrom/To`。
- 本地 `recommend_movies` 工具支持上映日期范围、`release_date_preferred` 和观影日期/时段；对应 `POST /internal/recommendations` 接收同义驼峰参数。日期偏好结果包含真实 `release_date` 和 `matches_release_window`；观影条件结果还包含实际可订购场次摘要。

默认的 `search_movies(query)` 仍调用旧 `/internal/movies`，返回影片资料列表；默认的 `search_screenings` 仍查询可订购场次。

新 Java 接口 `GET /internal/movies/query` 接收 `query`、`movieScope`、`screeningDate`、`cinemaQuery`、`showingOnly`、`page`、`pageSize`。返回 `movie_scope`、`screening_date`、`from_date`、`time_zone`、`showing_only`、`page`、`page_size`、`total`、`has_more`、`items`。排期影片包含 `screening_count`、`screenings` 与 `screenings_truncated`。

`GET /internal/screenings` 增加 `queryScope` 和 `showingOnly`，原 ID、片名、影院和日期条件继续适用。

接口继续要求内部服务凭证。身份、订单归属及账户撤销逻辑保持现有校验。

Agent 检查影片结果的范围、日期、分页和真实场次摘要；检查场次结果的必要字段与指定日期。数据契约不一致时返回 `query_contract_mismatch`，不把影片资料包装成排期结果。

## 时间诊断与回归

`temporal_summary` 随聊天响应及流式上下文输出，包含固定业务日期、时区、时间对象、解析状态、起止日期、早晚时段、条件强度和失败原因。持久化追踪只允许这些规范化字段，过滤用户原始时间表达及任意文本；规则指纹包含时间归一化模块。

固定测试日期为 `2026-10-13` 时，提问“你给我推荐悬疑题材的电影，最好是最近一周的电影，然后给我明确的时间信息”应产生一个 `recommend_movies` 任务：悬疑偏好、上映日期 `2026-10-07` 至 `2026-10-13`、软性日期偏好；不索要场次日期。答复列出实际上映日期，并标注范围外补充结果。

新增回归用例放在 `cinema-ai/tests/test_time_normalization.py`，覆盖原始问题、自然周和滚动周差异、跨月跨年和闰年、相对日期区间、软硬条件、短追问、自由片名继续提取、无效/模糊/冲突范围、工具参数不可篡改、结果日期校验、追踪过滤及完整 Agent 图执行。Java 隔离 H2 用例执行真实 SQL，验证日期边界、筛选先于数量限制、偏好排序、早晚场次及接口参数。

## 更新与验证

更新顺序：**Java 后端 → MCP → 内部 Agent**。需要部署新的后端包并重启这三个服务；依赖版本、数据库表结构和网关转接格式没有变更。若只更新 Agent 而保留旧 MCP/Java，新查询可能返回安全错误，需要配套更新。

本次验证使用隔离 H2 数据库（MySQL 模式）执行实际 SQL，以及本地真实 MCP HTTP 传输配合模拟 Java 数据。不读取线上密钥、不写入真实业务数据、不调用线上模型。覆盖上映无场次、未上映有排期、未开售/已开场、取消及停用、午夜边界、按电影分页、模型错误日期、连续追问、固定回答与原身份隔离。

本次补全需配套运行时间归一化、问题理解、任务规划、Agent 图、MCP 传输、追踪及工作流守卫的 Python 回归，以及 Java 查询服务与控制器的 H2 回归。Golden v1 留出验收集未修改。后端构建产物为 `cinema-ticketing-backend/target/cinema-ticketing-backend-0.0.1-SNAPSHOT.jar`。

2026-10-13 验证：上述 Python 回归 158 项通过，Java H2 查询与接口回归 15 项通过；Ruff 和变更空白检查通过，后端已重新打包。测试通过模拟模型执行，不依赖在线 Qwen/GLM 调用。

回归使用隔离业务数据及模拟模型，不代表网站已加载新版本。Java 后端、MCP 和内部 Agent 更新重启后才会在页面生效，生产 MySQL 仍需在部署环境验证。
