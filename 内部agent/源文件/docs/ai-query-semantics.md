# 内部 Agent 影片与排期查询规则

## 业务口径

- **影片资料（catalog）**：查询未下线影片的基础资料，不能证明有排期。
- **上映中（showing）**：当前影片状态为 `ON_SHELF` 或兼容旧数据的 `ON_SHOW`，且上映日期不晚于查询日期。上映日期为空时沿用声明状态。这个范围不要求有场次，也不使用开售时间判断上映。
- **已排期（scheduled）**：必须存在真实的 `SCHEDULED` 场次，影院和影厅均为 `ACTIVE`，影片未下线。包括未上映、未开售、当天已经开场的有效排期；排除已取消场次。
- **可订购（bookable）**：沿用现有售票规则，额外要求未开场、在影片开售窗口内等。没有可订购场次，不能推导出没有排期。
- **上映且有排期**：使用 `scheduled` 并显式设置 `showing_only=true`；普通排期查询不自动附加上映条件。

当前没有影片状态历史表，按历史日期查询“上映中”仍基于当前状态与上映日期，不能重建历史上架/下架过程。

## 日期与追问

1. Agent 在一次理解请求中固定北京时间日期。`今天/今日` 对应当天；`明天/后天` 按该日期偏移。明确日期和业务范围会覆盖模型的提取结果，模型不能删除、替换日期，或者自行切换为上映列表。
2. Java 使用 `Asia/Shanghai` 业务时钟。指定日期按开场时间的 `[当天 00:00, 次日 00:00)` 筛选，包含当天已开场的有效排期。
3. 排期未指定日期时查询北京时间今天及以后，并在回答中注明范围，不由模型猜日期。
4. 支持具体日期、月日、相对日期与星期。`本周三` 为本周的周三，`下周一` 为下一周周一，单独 `周三` 为今天或之后最近的周三。当前接口是单日查询；“下周/本月”这类未明确某一天的范围会请求补充日期。无效日期先澄清，不执行去掉日期条件后的宽泛查询。
5. “那明天呢”“那后天呢”“第2页”“下一页”承接前一轮查询类型与明确片名。新的全量列表问题不沿用上一轮片名。
6. “今天有哪些电影”没有说明上映或排期，会先询问查询范围。

## 查询链路

明确的全量列表问题走确定规则 → MCP → Java → MySQL → 结果校验 → 固定事实回答。

片名/影院等自由表达仍可以通过模型提取，随后受固定业务范围、用户提供的实体和日期约束。影片和场次结果直接生成回答，不经过模型重新解释，也不检索长期记忆作为实时业务依据。推荐及其他业务保留原链路。

排期电影查询先用 `EXISTS` 筛选有实际场次的电影，再按电影分页和去重，不从前 50 个场次推导全部影片。每页默认 20 部、最多 50 部，返回电影总数、页码和是否有后续页。

场次计数和摘要分批查询，避免逐片请求数据库。每部电影最多展示 10 个场次摘要，整页摘要读取上限 2000 条；计数仍来自独立聚合。摘要未完整展示时明确提示。独立场次明细接口仍最多返回 50 条，回答显示前 12 条并提示限制。

## MCP 与 Java 接口

MCP 保留原有四个只读工具，扩展以下参数：

- `search_movies`：新增 `movie_scope=catalog|showing|scheduled`、`screening_date`、`cinema_query`、`showing_only`、`page`、`page_size`。日期格式为 `YYYY-MM-DD`。
- `search_screenings`：新增 `query_scope=scheduled|bookable` 和 `showing_only`。

默认的 `search_movies(query)` 仍调用旧 `/internal/movies`，返回影片资料列表；默认的 `search_screenings` 仍查询可订购场次。

新 Java 接口 `GET /internal/movies/query` 接收 `query`、`movieScope`、`screeningDate`、`cinemaQuery`、`showingOnly`、`page`、`pageSize`。返回 `movie_scope`、`screening_date`、`from_date`、`time_zone`、`showing_only`、`page`、`page_size`、`total`、`has_more`、`items`。排期影片包含 `screening_count`、`screenings` 与 `screenings_truncated`。

`GET /internal/screenings` 增加 `queryScope` 和 `showingOnly`，原 ID、片名、影院和日期条件继续适用。

接口继续要求内部服务凭证。身份、订单归属及账户撤销逻辑保持现有校验。

Agent 检查影片结果的范围、日期、分页和真实场次摘要；检查场次结果的必要字段与指定日期。数据契约不一致时返回 `query_contract_mismatch`，不把影片资料包装成排期结果。

## 更新与验证

更新顺序：**Java 后端 → MCP → 内部 Agent**。需要部署新的后端包并重启这三个服务；依赖版本、数据库表结构和网关转接格式没有变更。若只更新 Agent 而保留旧 MCP/Java，新查询可能返回安全错误，需要配套更新。

本次验证使用隔离 H2 数据库（MySQL 模式）执行实际 SQL，以及本地真实 MCP HTTP 传输配合模拟 Java 数据。不读取线上密钥、不写入真实业务数据、不调用线上模型。覆盖上映无场次、未上映有排期、未开售/已开场、取消及停用、午夜边界、按电影分页、模型错误日期、连续追问、固定回答与原身份隔离。

验证结果：Java 查询与接口 10 项、Python 问题理解及回答 16 项、MCP 与 Agent 集成 16 项，共 42 项通过；Ruff 检查、后端打包与变更空白检查通过。后端构建产物为 `cinema-ticketing-backend/target/cinema-ticketing-backend-0.0.1-SNAPSHOT.jar`。

尚未在远程服务器部署或验证生产 MySQL。本机检查时相关服务未监听，本次交付为源码和构建产物，重启部署后才会在页面生效。
