# Dify 优先、按需转接内部 Agent：方案比较

日期：2026-09-27。状态：用户已选择方案 B，首期实现与启动说明见 [dify-agent-setup.md](dify-agent-setup.md)。以下保留方案比较及后续方向，未列入首期说明的能力仍为设计。

## 目标与假设

大多数常见咨询由你维护的 Dify 工作流完成。需要实时业务数据、知识不足或用户主动要求时，显示“转接实时助手”；用户点击后才将必要上下文交给内部 AI Agent。本文的“实时”指文本流式回复，语音和真人客服可另外设计。

Dify 的模型与工作流运行在 Dify 服务端，前端提供聊天入口、显示回复并处理转接。Java 负责用户身份、业务数据和订单状态。降低 Java 压力需要减少进入 Java 的请求及长连接，而不仅是换一个模型服务。

## 设计时的原有能力（接入前）

- Java `/api/ai/chat` 与 `/api/ai/stream` 验证登录后，将用户身份及问题传给独立 Python Agent。
- 内部查询工具已有影片、场次、本人订单、退票规则、知识检索和推荐接口。
- 工具通过 Java 内部 HTTP 接口查询，SQL 由 Java 编写。目前没有让模型执行任意 SQL 的入口。
- Python `/ai/stream` 目前先生成完整答案，再发送一个 SSE 事件，不是真正逐段生成。
- Java 当前流式转发使用阻塞 HTTP 客户端，继续作为所有聊天的入口会承担连接与线程负载。
- 原前端通过 Dify 官方嵌入气泡提供聊天，没有本站控制的完整转接流程；方案 B 首期现已替换该气泡，具体实现以启动说明为准。

## A：Dify 官方嵌入入口 + 手动转接

常见咨询：前端中的 Dify 嵌入页面 ↔ Dify，Java 不参与。

转接：用户点击网站自己的转接按钮 → Java 登录校验 → 内部 Agent → Java 业务工具 → 返回网站自己的助手界面。

优点：常见咨询能完全绕开 Java；接入工作量较少，可沿用官方嵌入功能和现有内部 Agent。

代价：跨域 iframe 的聊天 DOM 和响应不能由宿主前端随意读取。官方嵌入文档没有承诺完整的会话转接事件协议，需要按部署版本确认是否提供受支持的通信桥。第一版可让用户填写待处理问题，并携带当前影片/订单页面上下文，不能保证自动无损复制整段 Dify 对话。

适用：优先快速上线，可接受两个对话入口和部分上下文需重新输入。

## B：自定义聊天界面 + 独立轻量 AI 网关（推荐）

常见咨询：前端 ↔ AI 网关 ↔ Dify。

转接：前端 → Java 验证登录并签发短期转接凭证；前端携带凭证接入 AI 网关 → 内部 Agent → Java 业务工具 → Redis 或 MySQL。回复经 AI 网关直接流回前端，不再进入 Dify，也不让 Java 转发整段模型回复。

AI 网关负责 Dify 密钥、会话标识、流式连接、转接协议、限流和超时。可以采用独立部署的异步 Python 服务；是否与现有 Agent 合并进程，应由并发规模决定。它不直接连接业务数据库。

Java 负责登录校验、签发有限范围的转接凭证，以及实际业务查询。普通 Dify 咨询不需要 Java 登录校验；Dify 使用匿名或由网关生成的独立会话标识。Java 仅在用户选择处理本人业务时验证身份。

优点：一个连续的聊天界面；前端能可靠读取自己接收的答案与转接状态；Java 不承担普通咨询和模型长连接。

代价：增加一个需要维护的服务与会话协议；网关仍承受全部聊天的网络流量，需要独立资源、连接限制与监控。自托管 Dify 若与 Java 同机，仍会竞争机器资源。

适用：希望实现你描述的“前端监测、用户选择转接、内部 Agent 查询 Java、数据回到同一聊天窗口”。

## C：沿用 Java 作为统一 AI 入口

常见咨询：前端 ↔ Java AI 网关 ↔ Dify。

转接：用户确认 → Java → 内部 Agent → Java 业务工具 → Redis 或 MySQL → 同一聊天窗口。

优点：登录和权限集中，能沿用现有 Java 网关，新增部署组件较少。

代价：全部咨询请求和回复连接仍经过 Java。Dify 减少的是内部 Agent 执行和业务查询，Java 的 HTTP 流量及连接数未必下降。当前阻塞转发方式还需做异步转发、独立执行资源及并发限制。

适用：流量不大，优先复用当前代码、减少独立服务运维。

## B 方案的分工边界

### Dify 负责

- 通用观影须知、会员说明、操作引导、影片剧情及类型推荐。
- 未命中知识时询问必要参数，或建议用户转接。
- 公开片单可通过发布时同步的快照回答，带更新时间；不把快照中的价格、场次或余座承诺为实时状态。
- 退票政策说明需要版本同步；“我现在能否退这笔订单”转内部 Agent 查当前结果。

### 前端负责

- 显示 Dify 回答、内部助手回复和来源标识。
- 根据结构化转接状态显示按钮，保留用户随时主动转接的入口。
- 用户点击后提交当前问题、必要的最近对话、页面位置和影片/影院/订单引用。
- 展示连接中、查询中、生成中、失败与重试状态；重试复用 requestId，避免重复业务操作。
- 用户选择转接之前不启动内部 Agent，避免 Dify 与内部 Agent 同时处理每条消息。

### 内部 Agent 负责

- 理解意图、补齐参数，选择有限的业务工具，组织可读答案。
- 例如 `searchScreenings(movieId, date, cinemaId)`、`queryMyOrder(orderNo)`、`checkRefundEligibility(orderNo)`。
- 由工具提供权威结果、查询时间和数据来源；不根据前端传来的订单金额或模型生成的 userId 判定身份和资格。
- 第一阶段以查询与操作引导为范围；未来若接入退票等写操作，展示具体订单和结果供用户确认，再调用已有 Java 事务服务。付款继续走支付页面及服务端验证。

### Java 负责

- 从已认证会话识别用户，签发短期、限定用户及用途的转接凭证。
- 内部工具请求同时验证服务身份和用户范围。userId 由可信凭证导出，Agent 的普通参数不能覆盖。
- 固定业务接口、参数化查询、权限检查、分页及结果数量限制。
- 订单、锁座、支付、退票等事务和最终业务判断。

## 查询数据是否必须执行 SQL

不必每次访问 SQL，但业务查询都应通过 Java 的受控工具接口。

- 影片介绍、公开影院资料：缓存或公开快照，未命中时查询 SQL。
- 公开未来排期：短时缓存配合版本或变更失效，开场与周期过滤仍按当前时间处理。
- 本人订单：按用户范围实时查询，可由一次聚合接口同时返回座位、场次和状态。
- 余座：Redis 锁信息与持久化订单状态共同计算，选座时重新校验。
- 退票资格：Java 以当前订单状态、场次时间和启用规则判断；执行退票时再次校验。

缓存键必须包含影响结果的日期、影院和用户范围。用户订单不可进入通用知识库或跨用户缓存。后台编辑、场次取消、出票或退票后需要失效对应缓存。

## 转接契约（待你选择方案后共同确定）

建议由网关将工作流结果归一为 `answer`、`handoffSuggested`、`reason`、`intent`、`missingFields`、`sources` 与 `knowledgeVersion`。

这些是项目拟定字段，并非 Dify 所有应用天然返回的字段。Workflow 可配置 Output 节点输出结构化变量；Chatflow 需要结合所部署版本的 Answer、变量和流式事件，约定可解析的输出方式。

前端不扫描“我不知道”“查询失败”等自然语言来决定转接。业务意图、知识命中、缺失字段及上游错误形成明确状态；模型自报的置信度只能辅助。

用户转接请求包含 sessionId、requestId、当前问题、必要的最近对话和页面上下文。Dify API Key、内部服务凭证及身份主键都不作为聊天内容传递。订单号是查询线索，不能替代归属校验。

转接授权由 Java 验证；浏览器提供的历史、摘要和引用只用于对话理解。需要时从受支持的 Dify API 校核会话记录，不能把前端转接标记当成权限凭据。

## 实时交互

文本回复采用 SSE 即可；本次需求不要求为了“实时”引入双向 WebSocket。支持用户停止生成、连接超时、错误事件、有限重试和终态去重。

内部 Python Agent 应逐段产出真实生成事件；AI 网关统一 Dify 与内部 Agent 的事件格式，前端处理 `status`、`delta`、`result`、`error`、`done` 等项目事件。项目事件名不是 Dify 原生事件名。

转接后保持内部助手接管当前会话，提供用户主动返回常见咨询的入口，避免同一问题在两个 Agent 间反复跳转。公开 FAQ 可匿名访问，本人订单查询要求登录。

## 减压效果与判断标准

不预先承诺下降比例。观察 FAQ 独立解决率、转接率、每次转接的工具调用次数、Java 活跃流式连接、SQL 查询量、缓存命中率及回复延迟。

示例仅用于说明：1,000 条咨询，20% 转接、每条转接平均 2 次工具查询，则约有 400 次 Java 工具请求；若其中一半命中缓存，且未命中每次只执行 1 条 SQL，则约 200 条 SQL。身份校验、普通购票和日志等请求另计。C 方案中 Java 仍收到全部 1,000 条聊天请求。

建议为每轮设置工具调用次数、查询结果条数和执行时间上限；达到上限先澄清或提示失败，不反复调用查询。

## 建议实施顺序

1. 选择 A/B/C，确认 Dify 是自托管还是云服务、实际应用类型、工作流输出和部署资源。
2. 接入 FAQ，并实现用户主动转接、登录校验和真实流式回复。
3. 先开放本人订单、场次和退票资格三个只读工具，限制查询次数，记录观测指标。
4. 加入公开数据同步、缓存失效及结构化转接建议；根据指标决定是否扩大缓存或调整资源。
5. 用户明确选择后，再设计 Agent 写操作与真实支付接入。
